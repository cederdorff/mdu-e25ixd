Hvad er en teknisk audit?

Undersøg først — vælg forbedringen bagefter

Kort fortalt

En afgrænset undersøgelse af en eksisterende løsning. Fund dokumenteres og vurderes efter konsekvens.

Evidens er noget, andre kan efterprøve: fx kodehenvisning, skærmbillede, konsol/Network eller keyboard-flow.

Det hjælper jer med at

  • skelne problemer fra personlige præferencer
  • bevare et udgangspunkt til før/efter
  • vælge forbedringer med størst relevant effekt
Afgræns→Baseline→Undersøg→Prioritér→Forbedr→Verificér

I Case 1: Auditobjektet er Mellemrum. Tilmeldingsflowet og den deployede løsning skal altid indgå.

Hold definitionen kort og brug den som ramme for resten af dagen. Audit betyder ikke, at alt skal vurderes eller laves om; undersøgelsen skal være afgrænset og føre til begrundede valg. Målet er ikke at finde flest fejl, men at træffe bedre tekniske beslutninger om Mellemrum. Evidens er dokumentation, som en anden kan efterprøve og bruge til at forstå fundet. Evidens: to konkrete filer · Konsekvens: en API-ændring skal laves begge steder

Vigtigt: Eksemplerne viser formen — de er ikke fund i Mellemrum, før I selv har observeret og dokumenteret dem.

Bed holdet formulere forskellen i eksemplerne. De højre formuleringer er illustrative og skal ikke læses som facit på Mellemrums nuværende problemer. Eksemplerne er valgt, fordi de kan undersøges med værktøjer, de allerede kender: browseren, tastaturet, DevTools og editoren. De bliver kun gyldige auditfund, hvis de selv kan reproducere observationen, gemme evidens og forklare konsekvensen. En label, en button eller en service kan være en mulig løsning, men løsningspræferencen er ikke selve fundet. Et auditfund forbinder observation, evidens og konsekvens; løsningen kan stadig diskuteres. [Sources] - Teknisk audit af en React-løsning · lokalt kursusmateriale [/Sources]

Når I er færdige En synlig første leverance
  • mindst to gennemførte flows
  • tre rækker i audit-skabelonen

Hvorfor vente med at rette? I bevarer jeres baseline, adskiller observation fra løsning og kan prioritere fundene, før I bruger tid på implementering.

Side effect og Effect

Render beregner UI — useEffect kører efter render

01 · State 
const [posts, setPosts] =
  useState([]);
React husker posts mellem renders.
02 · Effect med side effect 
useEffect(() => {
  async function getPosts() {
    const response = await fetch(URL, { headers });
    setPosts(await response.json());
  }
  getPosts();
}, []);
fetch kontakter et system uden for React.
03 · Render 
return posts.map(post =>
  <PostCard
    key={post.id}
    post={post}
  />
);
JSX beregnes fra den aktuelle state.

Side effect er handlingen uden for render. Effect er Reacts navn for synkroniseringen, som deklareres med useEffect.

“Side effect” er det generelle begreb for arbejde, der påvirker eller bruger noget uden for den rene renderberegning. React-dokumentationen kalder en synkronisering, som skyldes rendering og deklareres med useEffect, en Effect. Ikke alle side effects skal i useEffect: handlinger, der skyldes et konkret klik eller submit, hører normalt i event handleren. En beregning baseret på eksisterende props/state behøver normalt slet ikke et Effect. Kodeudsnittet er forkortet. Én ejer: Kun CreatePage har caption-state. PostForm får værdien som prop og melder brugerens ændring tilbage.

export function formatPostDate(dateString) {
  if (!dateString) return "";

  const date = new Date(dateString);

  const formattedDate = date.toLocaleDateString("da-DK", {
    year: "numeric",
    month: "long",
    day: "numeric"
  });

  return formattedDate;
}
