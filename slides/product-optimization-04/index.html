02 Fagligt indspark

React-arkitektur

Hvor bor ansvaret — og hvor bevæger data sig?

Arkitektur er dagens største faglige indspark. Knyt alle principper til konkrete steder i Mellemrum og til deres auditfund. [Sources] - React: Thinking in React · https://react.dev/learn/thinking-in-react [/Sources]
Et praktisk blik på arkitektur

Arkitektur er placeringen af ansvar

Hvem koordinerer siden?

Hvem viser UI?

Hvem henter og gemmer data?

Hvem formaterer og genbruger logik?

God struktur reducerer antallet af steder, du skal forstå og ændre samtidig.

Arkitektur er ikke primært et bestemt mappetræ. Det er, om ansvaret er tydeligt nok til, at udviklere kan følge en ændring gennem løsningen. [Sources] - React: Thinking in React · https://react.dev/learn/thinking-in-react [/Sources]
En mulig ansvarsfordeling

Fire steder har fire forskellige hovedopgaver

pages/Koordinerer en routeData, page state og sammensætning
components/Viser genbrugelig UIProps ind · events ud
services/Taler med omverdenenSupabase-requests og mutationer
utils/Transformerer dataDatoer, tider og andre pure funktioner

Det er en arbejdshypotese — ikke et universelt facit.

Brug modellen som en linse, ikke som en obligatorisk mappestruktur. Et lille projekt kan have færre lag; spørg om placeringen gør ansvaret tydeligt. [Sources] - Case 1-casebeskrivelsen · lokalt kursusmateriale - React: Thinking in React · https://react.dev/learn/thinking-in-react [/Sources]

Separation of concerns

Render beregner UI — Effects synkroniserer med omverdenen

function EventsPage() {
  const [events, setEvents] = useState([]);

  useEffect(() => {
    fetchEvents().then(setEvents);
  }, []);

  const upcomingEvents = events.filter(isUpcoming);

  return <EventList events={upcomingEvents} />;
}

EffectKontakt til et eksternt system

BeregningDerived data under render

KompositionUI sammensættes af komponenter

Render-kode skal være pure. Effects bruges til synkronisering med eksterne systemer; en beregning baseret på eksisterende props/state behøver normalt ikke et Effect. [Sources] - React: Synchronizing with Effects · https://react.dev/learn/synchronizing-with-effects [/Sources]
Single responsibility

En komponent skal have ét forståeligt hovedansvar

Undersøg komponenten, når…

  • navnet ikke længere beskriver hele filen
  • dataadgang, formatering og meget UI er blandet
  • ændringer ét sted ofte påvirker noget andet
  • samme del gentages eller er svær at teste alene
Stor er et signal — ikke i sig selv et problem.
Undgå en mekanisk linjegrænse. Spørg i stedet, om komponentens ansvar kan beskrives klart i én sætning, og om en udtrækning giver en reel grænse. [Sources] - React: Thinking in React · https://react.dev/learn/thinking-in-react [/Sources]
Component composition

Sammensæt siden af dele med tydelige kontrakter

function EventDetailsPage() {
  return (
    <main>
      <EventHeader event={event} />
      <EventFacts event={event} />
      <RegistrationForm eventId={event.id} />
    </main>
  );
}

EventHeaderpræsenterer identitet

EventFactsviser formatterede eventdata

RegistrationFormejer tilmeldingsinteraktionen

Delkomponenter skal ikke opstå kun for at gøre filen kortere. De skal have et navn, et ansvar og en forståelig kontrakt via props/events. [Sources] - React: Thinking in React · https://react.dev/learn/thinking-in-react [/Sources]
Ensrettet dataflow

State har én ejer — data går ned, handlinger går op

EventDetailsPageejer event
props ↓↑ callbacks
EventHeaderlæser event
RegistrationFormsender handling op

Single source of truth betyder én ejer pr. information — ikke én global state til alt.

Hvis to komponenter skal være enige om samme information, flyttes state ofte til deres nærmeste fælles parent. [Sources] - React: Sharing State Between Components · https://react.dev/learn/sharing-state-between-components [/Sources]
Derived state

Kan værdien beregnes, skal den normalt ikke gemmes igen

Undgå dobbelt sandhed 
const [events, setEvents] = useState([]);
const [eventCount, setEventCount] = useState(0);
Beregn ud fra kilden 
const [events, setEvents] = useState([]);
const eventCount = events.length;

Spørg: Kan denne værdi beregnes fra eksisterende props eller state under render?

Redundant og duplikeret state kan komme ud af sync. Gem den minimale, komplette state og beregn resten. [Sources] - React: Thinking in React · https://react.dev/learn/thinking-in-react - React: Choosing the State Structure · https://react.dev/learn/choosing-the-state-structure [/Sources]
Tilbage til auditten

Brug arkitekturen som fem nye undersøgelsesspørgsmål

  1. Kan jeg forklare hver vigtig fils hovedansvar?
  2. Er dataadgang og præsentation blandet på en måde, der gør ændringer svære?
  3. Har hver information én tydelig ejer?
  4. Er noget gemt som state, selvom det kan beregnes?
  5. Er gentaget formatering placeret ét forståeligt sted?

Vælg ét spørgsmål, og dokumentér ét konkret fund i Mellemrum.

Kort arbejdspas: 10–15 minutter. De skal koble princippet til en konkret fil og undgå at refaktorere endnu. [Sources] - Teknisk audit af en React-løsning · lokalt kursusmateriale [/Sources]
03 Repetition

Styling i React

Tre tilgange — og ét fælles behov for konsistens.

Dette er en repetition. Fokusér på struktur og valg, ikke på at lære ny CSS. [Sources] - React: Common components · https://react.dev/reference/react-dom/components/common - Vite: Features · https://vite.dev/guide/features [/Sources]
Tre gyldige tilgange

Vælg ud fra rækkevidde og ansvar

GlobaltKlassisk CSS

Fælles stylesheet og globale class names.

Godt til reset, tokens, layout og fælles mønstre.
LokaltCSS Modules

Styles importeres som et modul.

Godt til komponentnære styles uden navnekollisioner.
DynamiskInline styles

Et JavaScript-objekt på elementet.

Godt når værdien faktisk kommer fra data.
React foreskriver ikke én CSS-metode. Vite understøtter almindelige CSS-importer og behandler .module.css som CSS Modules. [Sources] - React: Common components · https://react.dev/reference/react-dom/components/common - Vite: Features · https://vite.dev/guide/features [/Sources]
01 · Klassisk CSS

Globale class names gør fælles styling enkel

import "./styles.css";

export function EventCard() {
  return <article className="event-card">…</article>;
}
.event-card {
  padding: var(--space-md);
  border-radius: var(--radius-md);
}
Styrke: let at dele på tværs · Pas på: kaskade, specificitet og navnekollisioner
Klassisk CSS er ikke en “forkert” eller gammel løsning. Auditspørgsmålet er, om globale regler og navne er organiseret og forudsigelige. [Sources] - React: Common components · https://react.dev/reference/react-dom/components/common [/Sources]
02 · CSS Modules

Lokale class names gør komponentens styling tydelig

import styles from "./EventCard.module.css";

export function EventCard() {
  return <article className={styles.card}>…</article>;
}
.card {
  padding: var(--space-md);
  border-radius: var(--radius-md);
}
Styrke: lokal scope og tydelig relation · Pas på: fælles mønstre må ikke kopieres overalt
I Vite bliver filer, der slutter på .module.css, behandlet som CSS Modules og importen returnerer et module object. [Sources] - Vite: Features · https://vite.dev/guide/features [/Sources]
03 · Inline styles

Brug inline styles, når værdien kommer fra JavaScript

<div
  className="progress"
  style={{ "--progress": `${percent}%` }}
>
  {percent}%
</div>

Godt matchstørrelse, position eller custom property fra data

Svagt matchhele komponentens statiske styling som store objekter

HuskCSS-properties skrives normalt i camelCase

React anbefaler style-proppen til dynamiske værdier, som ikke kendes på forhånd; ellers er className og CSS mere effektivt. Custom properties kan bruges som en smal bro mellem data og CSS. [Sources] - React: Common components · https://react.dev/reference/react-dom/components/common [/Sources]
Fælles fundament

:root-variabler gør designvalg genbrugelige

:root {
  --color-brand: #173f35;
  --color-accent: #d8ff62;
  --space-sm: 0.75rem;
  --space-md: 1.5rem;
  --radius-md: 0.75rem;
}

.event-card {
  padding: var(--space-md);
}

Én definitionfærre magic values

Semantiske navneintention frem for tilfældig hex

Kan bruges overaltklassisk CSS, Modules og inline

CSS custom properties definerer genbrugelige værdier og læses med var(). Semantiske tokens gør ændringer og audit lettere. [Sources] - MDN: Using CSS custom properties · https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties [/Sources]
Tilbage til auditten

Undersøg om stylingens struktur matcher dens rækkevidde

Globalt: Hvilke regler og variabler skal gælde hele appen?

Lokalt: Hvilke styles hører tydeligt til én komponent?

Dynamisk: Hvilke værdier afhænger faktisk af JavaScript?

SPA-problemet

UI’et skifter side — men browseren genstarter ikke oplevelsen

Traditionel navigation Nyt dokument

Browseren indlæser siden og starter en ny læsekontekst.

Client-side routing Samme dokument

URL og indhold skifter, men fokus kan blive i navigationen og titlen kan være uændret.

Resultat: Nogle brugere får ikke et tydeligt signal om, hvor de er landet.

Client-side route changes giver ikke automatisk den samme oplevelse som en fuld page load. Fokus kan blive ved det aktiverede link, og screen reader-brugere kan mangle kontekst. [Sources] - Gatsby: User testing of accessible client-side routing · https://www.gatsbyjs.com/blog/2019-07-11-user-testing-accessible-client-routing/ [/Sources]
Routing og sideskift

Et sideskift skal give både identitet og et nyt startpunkt

01Opdatér sidens titel

document.title beskriver den aktuelle route i fanen og dokumentet.

02Flyt fokus meningsfuldt

Fokusér fx den nye h1, så keyboard- og screen reader-brugere lander i indholdet.

Titel alene annonceres ikke nødvendigvis dynamisk — derfor skal hele navigationsoplevelsen testes.

En præcis titel beskriver sidens formål. MDN bemærker også, at dynamiske titelændringer ikke automatisk annonceres af alle screen readers. Fokus eller live announcements kan derfor stadig være nødvendige. [Sources] - MDN: title element · https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/title - MDN: Document.title · https://developer.mozilla.org/en-US/docs/Web/API/Document/title [/Sources]
Fokus-styring i React

Route-komponenten kan etablere den nye kontekst

function EventPage({ event }) {
  const headingRef = useRef(null);

  useEffect(() => {
    document.title = `${event.title} · Mellemrum`;
    headingRef.current?.focus();
  }, [event.title]);

  return (
    <main>
      <h1 ref={headingRef} tabIndex={-1}>
        {event.title}
      </h1>
    </main>
  );
}

useRefpeger på den nye overskrift

tabIndex={-1}gør den programmatisk fokusérbar

useEffectkører efter den nye UI er rendret

Testfokus skal være synligt og opleves logisk

Patternet er bevidst enkelt til Mellemrum. I React 19 kan title også renderes fra en page-komponent, men projektets version og routing skal kontrolleres. [Sources] - React: Common components, manipulating a DOM node with a ref · https://react.dev/reference/react-dom/components/common - React: title · https://react.dev/reference/react-dom/components/title - Gatsby: Accessible client routing research · https://www.gatsbyjs.com/blog/2019-07-11-user-testing-accessible-client-routing/ [/Sources]
