Online · Så konfigurationen

Vi løser to forskellige Pages-problemer

1

Adresser til routes og filer

Pages tilføjer repositoryets navn foran appen.

Build
Vites base retter stier til JavaScript, CSS og importerede billeder.
Public-billeder
${import.meta.env.BASE_URL}logo.webp
Routes
basename={import.meta.env.BASE_URL}
2

Refresh på en app-route

Pages er en filserver og kan ikke selv finde en React-route som /posts.

Direkte URL eller refresh Pages finder ingen fil 404.html → React-appen React Router læser URL’en og viser siden

Base path retter adresserne. Fallback starter appen ved en direkte route.

Hold de to problemer adskilt. Problem 1 handler om adresser: Vite retter genererede buildstier og importerede assets automatisk ud fra base. Filer i public refereres i starteren med BASE_URL, og BrowserRouter bruger den samme værdi som basename. Problem 2 opstår først ved en direkte URL eller refresh: GitHub Pages leder efter en fysisk fil, men /posts er en route i browseren. Workflowet kopierer derfor index.html til 404.html, så React kan starte og routeren kan læse URL’en. Skeln mellem to fejl

En forventet Supabase-fejl på /posts er okay nu. En GitHub 404 eller manglende billeder betyder, at Pages-konfigurationen ikke er færdig.

Dette er dagens centrale live-demo. Vis først base i package.json og at Pages bruger GitHub Actions. Lav en synlig ændring i HomePage.jsx, kør npm run build, review diffet, commit og push til main. Synlighed · En vigtig grænse

Skjult fra Git er ikke det samme som hemmeligt

Værdien står ikke direkte i komponenten eller repositoryet. Men Vite indsætter VITE_-værdier i frontendens build.

Ikke synlig i Git

.env ignoreres, så de konkrete værdier ikke bliver committed eller vist i repositoryet.

Kan findes i browseren

En bruger kan finde værdierne i JavaScript-buildet eller i appens netværkskald.

Brug kun Supabase URL og publishable key i frontend — aldrig passwords, private tokens eller service-keys.

Skeln mellem tre ting: Værdien er ikke hardcoded i komponenten, den ligger ikke i Git-repositoryet, men den er stadig tilgængelig for den færdige browserapp. VITE_-prefixet er Vites mekanisme til at eksponere en værdi til klientkoden; det er ikke kryptering. Vis eventuelt DevTools Network og request-headeren apikey. Brug kun de udleverede frontend-værdier i øvelsen. Supabase Data REST API

Databasen bliver til HTTP-endpoints

const response = await fetch(
  `${SUPABASE_URL}/rest/v1/posts`,
  {
    headers: {
      apikey: PUBLISHABLE_KEY,
      "Content-Type": "application/json"
    }
  }

const posts = await response.json();

Projekt + /rest/v1/ + tabel.

HTTP

Metode, headers, query-parametre og body.

Svar

Statuskode, headers og JSON-data.

Din kode

Håndterer loading, fejl og tomme resultater.

REST og JavaScript SDK

Samme intention — forskellig mængde håndarbejde

Direkte REST med fetch

const response = await fetch(URL, {
  headers: { apikey: key }
});

if (!response.ok) {
  throw new Error("Kunne ikke hente posts");
}

const data = await response.json();

Supabase JavaScript SDK

const { data, error } = await supabase
  .from("posts")
  .select("*");

if (error) {
  throw error;
}

SDK’et giver os et mere specialiseret sprog til API’et.

Forklar at supabase-js stadig kommunikerer med Supabase-tjenesterne. Query builderen samler URL, headers og parsing i et bibliotek med Supabase-begreber. [Sources] - https://supabase.com/docs/reference/javascript/initializing - https://supabase.com/docs/reference/javascript/select [/Sources]
Hvad får vi med SDK’et?

Én klient samler flere Supabase-produkter

Database

Læs, opret, opdatér, slet, filtrér og hent relationer med en query builder.

Auth

Login, sessioner, brugerdata og tokens i samme klient.

Realtime

Lyt til ændringer og byg interfaces, der opdaterer løbende.

Storage + Functions

Arbejd med filer og kald server-side Edge Functions.

Vi vender tilbage til SDK’et, når auth, relationer og mere avanceret dataarbejde gør abstraktionen værdifuld. [Sources] - https://supabase.com/docs/reference/javascript/introduction [/Sources]

Når alt virker vigtigt

Prioritér efter konsekvens — ikke efter hvor let det ser ud

Appen kan ikke bruges

Build, deployment, routing, data eller blokerende runtime-fejl.

Brugere bliver udelukket

Tastatur, labels, fokus, kontrast eller utilgængelige handlinger.

Løsningen er misvisende

Forkert identitet, metadata, indhold eller uforståelige fejl-states.

Koden kan forbedres

Oprydning, navngivning og struktur uden akut bruger- eller driftskonsekvens.

Prioriteringen er en tommelfingerregel. Bed de studerende skrive én sætning: “Vi vælger X først, fordi Y”. [Sources] - User-provided lesson goals and starter-repository audit scope, 17 August 2026 [/Sources]
