Hvorfor branches og pull requests?

Arbejd samtidig — uden at ødelægge live-sitet

Alle pusher direkte til main
  • SamarbejdeTo i samme fil — konflikter direkte på main
  • KvalitetIngen styr på main — alt går direkte live
  • Overblikfix, update, asdf — hvem og hvorfor?
Branches og pull requests
  • SamarbejdeHver i sin branch — konflikter løses dér
  • KvalitetStyr på main — kun det, der er set i en PR
  • OverblikPull requesten forklarer hvad og hvorfor

Branches = I kan arbejde samtidig. Pull requests = kun det, der er klar, kommer ind i main — og går live.

Hold branches små og afgrænsede

Én opgave = én kort branch

Én stor branch i to uger

KonflikterKæmpe pull requestLænge til live

Jo længere den lever, jo længere løber main fra den

Små branches, merget hurtigt

Færre konflikterLet at læseHurtigt live

Afgrænset: Kan I ikke navngive den kort, er den for stor

Hvorfor smart? Jo kortere tid en branch lever, jo mindre når main at ændre sig — og jo lettere er pull requesten at forstå for resten af gruppen.

Anbefalinger · ikke verdensmesterskab

Gør det så godt, som I kan

Skal

Det skal være på plads

  • Public repo på GitHub
  • Appen er deployet på Vercel
  • main virker

Anbefalet

Det prøver I at gøre

  • Branches og pull requests
  • Små branches og små commits
  • De seks gode vaner

Ekstra godt

Når det kører

  • En anden kigger med og merger
  • Gode beskrivelser i pull requests

Jeg forventer ikke, at I er verdensmestre i Git. Går noget galt, kan det næsten altid fixes — og spørg hellere én gang for meget.
