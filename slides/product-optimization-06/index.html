Lighthouse er en kontrolleret lab-test. Den viser ikke nødvendigvis det, alle virkelige brugere oplever.

Det vigtigste filterHvis vi ikke kan forklare betydningen for brugeren, har vi endnu ikke et prioriteret problem.

Svar eksplicit på spørgsmålet: Lighthouse er egnet til før/efter, hvis betingelserne holdes ens. Network er det vigtigste supplement på deres niveau. Gør forskellen eksplicit: Lighthouse er en kontrolleret lab-test, mens virkelige brugere har forskellige devices, netværk og interaktioner. Stop derefter ved brugerflowet: Hvem rammes? To forskellige testvalg

Inkognito og Disable cache løser ikke det samme

Inkognito Giver et renere testmiljø Reducerer påvirkning fra extensions og eksisterende IndexedDB-/browserdata.
Disable cache Simulerer bedre et første besøg Tvinger requests forbi browserens cache, mens DevTools er åbent.
God cold-cache-baseline Inkognito + DevTools åbent + Disable cache slået til

Kør derefter et separat warm-cache-run med Disable cache slået fra.

Sig forskellen direkte: Inkognito handler om testmiljøet. Disable cache handler om cache-scenariet. De kan bruges sammen, men de er ikke synonymer. Rapporten advarer om lagret IndexedDB-data, og Reduce unused JavaScript indeholder scripts fra browser-extensions; derfor er inkognito relevant. Disable cache gælder, mens DevTools er åbent, og gør cold-cache-runnet mere lig et første besøg. Kør også warm cache, fordi en tilbagevendende bruger kan få assets fra memory eller disk cache. Derfor kan dev mode vise to requests

Lokalt · development2 × GET /eventsStrict Mode kører Effects en ekstra gang for at afsløre problemer
→
Deployet · productionTypisk 1 × GET /eventsdet ekstra development-tjek kører ikke i production
  • Se først, om det dobbelte request kun findes lokalt.
  • Test Network på den deployede version, før du optimerer.
  • Sker det også dér? Undersøg dependencies og flere fetch-steder.
React Strict Mode kører ekstra udviklingstjek, herunder en ekstra setup/cleanup-cyklus for Effects i development. Det kan derfor ligne et dobbelt datarequest lokalt, selv om det ekstra tjek ikke køres i production. Ret ikke blindt ved at fjerne Strict Mode. Kontrollér først Network på den deployede version. Hvis requestet også er dobbelt dér, undersøges effectens dependencies og om samme fetch ligger flere steder. Lazy-load PostDetailPage — hvis første bundle er problemet

  import("./pages/PostDetailPage")

<Route
  path="/posts/:id"
  element={
    <Suspense fallback={<p>Indlæser post…</p>}>

    </Suspense>
  }

lazy()venter med at hente sidens JavaScript, til routen skal vises

Suspenseviser en fallback, mens komponentens kode bliver hentet

Tradeoffmindre første bundle — men et ekstra load, når detaljesiden åbnes første gang

Brug det kun, hvis første JS-load er et dokumenteret problem.
Knyt eksemplet til den eksisterende Post App: App.jsx forbinder allerede /posts/:id med PostDetailPage. En almindelig statisk import lægger normalt page-koden i den JavaScript, der er klar ved første load. lazy() bruger en dynamisk import og venter med at hente modulet, til PostDetailPage skal renderes. Suspense viser fallbacken imens. Modulet skal have en default export, hvilket den eksisterende PostDetailPage allerede har. Gevinsten er ikke mindre samlet kode, hvis brugeren besøger alle routes; koden flyttes til det tidspunkt, hvor den skal bruges. Vis derfor dette som et valgfrit, senere greb. De fleste studerende får mere ud af at optimere billeder og requests først. Et gyldigt resultat

“Vi fandt ikke et væsentligt performanceproblem”
