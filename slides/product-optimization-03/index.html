Fejlhåndtering

Gør forventelige fejl til en kontrolleret del af løsningen.

[Sources] - MDN: Using the Fetch API · https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch [/Sources]
Hvad · hvorfor · hvordan

Fejlhåndtering er en strategi

Hvad?

Opdag og håndtér fejl, vi ved kan opstå.

Hvorfor?

Undgå tavse fejl og fastlåste brugere.

Hvordan?

Validér responsen, fang fejlen og vælg næste state.

En fejl er ikke kun et teknisk problem. Den ændrer, hvad brugeren kan se og gøre.

[Sources] - MDN: Using the Fetch API · https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch [/Sources]

En vigtig fetch-detalje

fetch() afviser ikke en 404

Netværksfejl

Promise rejects

catch kan fange fejlen.

HTTP 404 / 500

Promise resolves

Kontrollér selv response.ok.

if (!response.ok) {
  throw new Error(
    "Kunne ikke hente events: " + response.status
  );
}
Dette er den centrale fetch-misforståelse. [Sources] - MDN: Using the Fetch API · https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch [/Sources]
Hvordan?

Gør alle udfald eksplicitte

async function getEvents() {
  setStatus("loading");
  try {
    const response = await fetch(url, { headers });
    if (!response.ok) throw new Error("HTTP " + response.status);

    const data = await response.json();
    setEvents(data);
    setStatus(data.length === 0 ? "empty" : "success");
  } catch (error) {
    console.error("Kunne ikke hente events", error);
    setStatus("error");
  }
}
Status bruges nu, men renderingen kommer i næste kapitel. [Sources] - MDN: Using the Fetch API · https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch - React: useState · https://react.dev/reference/react/useState [/Sources]

05Fagligt fokus

Robuste UI-states

UI’et skal give mening under hele processen — ikke kun efter succes.

[Sources] - React: Reacting to Input with State · https://react.dev/learn/reacting-to-input-with-state [/Sources]
Hvad · hvorfor · hvordan

En UI-state beskriver situationen nu

Hvad?

En tydelig visning af systemets aktuelle tilstand.

Hvorfor?

Brugeren forstår, om systemet arbejder eller kræver handling.

Hvordan?

Modellér states, og render det rigtige UI for hver state.

Robust betyder ikke fejlfri. Det betyder forståelig og brugbar — også når noget går galt.

[Sources] - React: Reacting to Input with State · https://react.dev/learn/reacting-to-input-with-state - React: Conditional Rendering · https://react.dev/learn/conditional-rendering [/Sources]
Fire grundtilstande

Ét dataflow — fire oplevelser

Loading

Vent

Requestet er i gang. Vis fremdrift.

Success

Brug

Data er klar. Vis indholdet.

Empty

Forstå

Requestet lykkedes, men data er tom.

Error

Kom videre

Noget fejlede. Forklar og hjælp.

Empty er ikke en fejl: serveren kan have svaret korrekt med et tomt array. [Sources] - React: Reacting to Input with State · https://react.dev/learn/reacting-to-input-with-state [/Sources]
Modellér tilstandene

Én status begrænser konflikter

Flere booleans 
isLoading = true
hasError = true
isEmpty = true

Kan UI’et være alle tre?

Én status 
const [status, setStatus] =
  useState("loading");

Kun én aktiv tilstand ad gangen.

En status-string er en enkel model til casen; komplekse flows kan kræve mere. [Sources] - React: Choosing the State Structure · https://react.dev/learn/choosing-the-state-structure [/Sources]
Render den aktuelle state

State skal kunne ses i UI’et

if (status === "loading") {
  return <p>Henter events…</p>;
}
if (status === "error") {
  return <ErrorMessage onRetry={getEvents} />;
}
if (status === "empty") {
  return <p>Der er ingen kommende events endnu.</p>;
}

return <EventGrid events={events} />;
Early returns holder hver state adskilt og let at læse. [Sources] - React: Conditional Rendering · https://react.dev/learn/conditional-rendering [/Sources]
